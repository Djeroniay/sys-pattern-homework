### Задание 1

Преимущества масштабирования методами master-slave репликации

1. Аактивный master-сервер и пассивный репликационный slave-сервер;

* Отказоустойчивость – при падении master нагрузка быстро переключается на slave, что сокращает время простоя.
* Разгрузка master – все тяжёлые отчётные и аналитические запросы идут на slave, master занимается только записью.
* Бэкапирование – резервные копии создаются на slave без остановки работы master.
* Тестирование – на slave можно безопасно проверять обновления и изменения без риска для production.
* Простота настройки – асинхронная репликация легко реализуется в большинстве СУБД.

2. master-сервер и несколько slave-серверов;

* Масштабирование чтения – нагрузка по SELECT-запросам распределяется между несколькими slave.
* Геораспределение – slave можно размещать в разных регионах для ускорения доступа пользователей.
* Специализация – разные slave используются для разных целей: отчёты, бэкапы, аналитика, веб-приложения.
* Высокая доступность – отказ одного slave не влияет на систему, остальные продолжают работу.
* Параллельная обработка – сложные запросы могут выполняться на нескольких slave одновременно.
* Обновления без простоя – серверы обновляются по очереди, система остаётся доступной.

### Задание 2

Вертикальный шардинг по функциональным доменам

Принцип: данные распределяются по разным серверам в зависимости от их тематики.

Схема:

Сервер А: пользователи.

Сервер Б: книги.

Сервер В: магазины .

Работа: каждый сервер отвечает за свой домен. Например, записи о пользователях отправляются на Сервер А, о книгах — на Сервер Б, о магазинах — на Сервер В. При необходимости на каждом сервере могут быть созданы slave-реплики для быстрого чтения.

Маршрутизация: приложение или API-шлюз перенаправляют запросы на нужный сервер в зависимости от типа данных.



Горизонтальный шардинг по данным

Принцип: каждая таблица делится на части (шарды) с помощью хеша от идентификатора. Для этого используется формула user_id % N, book_id % N и так далее.

Структура:

Шард 1: пользователи, книги, магазины с остатком хеша 0.

Шард 2: пользователи, книги, магазины с остатком хеша 1.

Шард 3: пользователи, книги, магазины с остатком хеша 2.

Функционал: каждый шард — мастер для своей части данных. Для отказоустойчивости у каждого есть свои slave-реплики.

Маршрутизация: специальный слой определяет, какой шард отвечает за конкретный запрос, и перенаправляет его туда.



Гибридная архитектура (вертикальный и горизонтальный шардинг)

Идея: сначала данные делятся по доменам (вертикальный шардинг), а затем, если в каком-то домене становится слишком много информации, его разбивают на части (горизонтальный шардинг).

Пример:

Пользователи: разделены на 3 шарда по user_id.

Книги: разделены на 3 шарда по book_id.

Магазины: остаются на одном сервере, так как их немного.

Мета-сервер: хранит данные о том, какой шард отвечает за какие записи. Это помогает маршрутизировать запросы.

Резервное копирование: у каждого шарда есть хотя бы одна реплика. Если мастер-сервер выходит из строя, запрос автоматически направляется на реплику.
